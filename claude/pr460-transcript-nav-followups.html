PR #460 — transcript-nav follow-ups

PR #460 ("Transcript navigation small followups") in meridianlabs-ai/ts-mono — two independent fixes, based on origin/main at 2e45a1fc. Follow-up to PR #354 (its report).

One decision for the reviewer. In fix 1, when a swimlane selection key no longer matches any row, this scopes rendering to the root row and keeps the stale key, so re-enabling the utility toggle restores the previous selection. #431 instead clears the selection for the analogous case when switching timelines. Both are defensible; if the clearing behaviour is preferred, fix 1 changes shape. Everything else here is mechanical.

Fix 1 — orphaned swimlane selection (cf6040b0, useTranscriptTimeline.ts, +14/−3)

Hiding the selected swimlane lane — which the utility-agent toggle does routinely — left a selection key matching no row, and rendering fell through to the unscoped event stream. The just-hidden events reappeared and the outline and turn counts inflated until another row was clicked. Regressed in #354.

An unmatched key is now treated as distinct from "nothing selected" and scopes to the root row. The key is deliberately kept, so toggling utility back on restores the selection.

Fix 2 — ?message= deep link armed live-follow (e9808ced, ChatViewVirtualList.tsx +11, SampleDisplay.tsx +1)

A ?message= deep link into a running sample armed live-follow, because ChatViewVirtualList never forwarded navOwned. The landing was then yanked to the tail as soon as the next message arrived, with no visible cause. Predates #354.

navOwned is now derived from initialMessageId and frozen at mount, mirroring TranscriptViewNodes. followRequested is forwarded alongside it, so an explicit ?follow=1 still tails and the messages tab agrees with the transcript tab.

Three things get in the way of staging this, so the steps are spelled out.

  1. The per-message copy-link control is deliberately hosted-only (isHostedEnvironment() — a localhost URL is not worth sharing), and Search cannot supply the link either because it is unavailable while a sample is still running. To obtain a ?message= URL locally, temporarily make that function return true in packages/util/src/vscode.ts. Local debug toggle only — revert it afterwards.
  2. Start a sample that stays running with a message available on demand. An idle running sample is not enough: an armed follow is invisible until a message actually arrives, because the deep-link scroll wins at mount either way. This offline task does it — it floods 40 steps, then blocks until a trigger file appears: 
    import asyncio, os
from pathlib import Path
from inspect_ai import Task, task
from inspect_ai.dataset import Sample
from inspect_ai.model import ModelOutput, get_model
from inspect_ai.solver import generate, use_tools
from inspect_ai.tool import tool

FAST, TOTAL = 40, 80
TRIGGER = Path("/tmp/msg_go")

@tool
def tick():
    async def execute(n: int):
        """Record step n.

        Args:
            n: Step number.

        Returns:
            Confirmation.
        """
        if n <= FAST:
            await asyncio.sleep(0.1)
        else:
            while not TRIGGER.exists():
                await asyncio.sleep(0.5)
            os.remove(TRIGGER)
        return f"step {n} complete"
    return execute

@task
def slow_messages():
    out = [ModelOutput.for_tool_call(model="mockllm/model", tool_name="tick",
           tool_arguments={"n": n}, content=f"Starting step {n}.")
           for n in range(1, TOTAL + 1)]
    out.append(ModelOutput.from_content("mockllm/model", "DONE"))
    return Task(dataset=[Sample(input="Run a job.", target=["DONE"])],
                solver=[use_tools(tick()), generate()],
                model=get_model("mockllm/model", custom_outputs=out))
    Run it with inspect eval <file>.py --log-dir ./logs; no API key needed.
  3. Open the running sample's Messages tab, hover an early ASSISTANT role label, click the link icon that appears, and open that URL in a second tab. It is a plain hash route, so the same URL also works against a build without these fixes.

Verification

Both fixes were confirmed in a browser by A/B: one build serving origin/main (so #354 present, these fixes absent) alongside one serving the branch. In each case the unfixed build reproduced the symptom and the fixed build did not — fix 1 via differing outline turn counts, fix 2 via the unfixed build jumping to the tail while the fixed build held position.

Four regression tests, each checked failing against the pre-fix revision of its own file:

  • useTranscriptTimeline.test.ts — "keeps the hidden events out when the utility toggle drops the selected lane", and a guard that a timeline with no rows still returns every event.
  • ChatViewVirtualList.test.tsx — "stands down on a ?message= landing into a live sample", and "an explicit follow=1 still arms on a ?message= landing". Both drive the real VirtualList and assert the persisted follow flag rather than mocking the component.

pnpm turbo run test lint typecheck format passes across the workspace, with one known pre-existing flake unrelated to this branch (a lazy-mathjax import test that exceeds vitest's default 5s timeout under parallel load and passes standalone).

Reproducing locally

Ports and paths below are one local dev setup — substitute your own log directory and any log containing utility agents.

Fix 1 needs a sample whose header offers to reveal hidden utility agents. Open it, reveal the utility lanes, click one and note the turn count and outline, then switch the utility toggle off while that lane is still selected. Before the fix the hidden events return and the counts inflate; after it, the view falls back to the main lane. Switching the toggle back on should restore the utility lane.

Fix 2 is harder to stage, because three things get in the way. The per-message copy-link control is deliberately hosted-only (isHostedEnvironment() — a localhost URL is not worth sharing), so obtaining a ?message= URL locally means temporarily making that function return true in packages/util/src/vscode.ts — a local debug toggle only, to be reverted. Search cannot supply the link either, as it is unavailable while a sample is still running. And a merely idle running sample shows nothing, because an armed follow is invisible until a message actually arrives: the deep-link scroll wins at mount either way.

What works is a throwaway offline task that emits a burst of messages and then waits on a trigger file, so one further message can be made to land on demand while the deep-linked tab is open. Any mock-model task with a tool that blocks on a sentinel file will do.
